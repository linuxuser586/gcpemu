## Resolver routes: `gcpemu dns install`

`gcpemu dns install` sends `svc.cluster.local` and `gke.internal` to the emulator's DNS, so host
tools reach GKE Services by name, as `curl http://web.default.svc.cluster.local:8080` (ADR 0026).
Add a `--suffix` for each emulated Cloud DNS zone the host should resolve too. `gcpemu dns
uninstall` removes only the routes that Instance added. It replaces the hand-written
`/etc/resolver` and `resolvectl` setup the README used to ask for, and works on Windows too:

- **Linux** (systemd-resolved): a dummy link, `gcpemu-dns0`, that lasts until reboot.
- **macOS**: one `/etc/resolver/<suffix>` file per suffix.
- **Windows**: one NRPT rule per suffix. NRPT can't name a port, so start the Instance with
  `--port dns=53` first.

It asks before it changes anything (`--yes` skips that, `--dry-run` only prints the commands) and
runs only that step as root, through sudo or UAC. `gcpemu status` lists the routes, and `gcpemu
doctor` reports any that are gone or point at another port. See "Kubernetes Services from the
host" in the README.

## The image is on distroless Debian 13

The OCI image's base moved from `gcr.io/distroless/static-debian12` to `static-debian13`. A
Containerized Instance trusts the CAs in its own container, so it now uses Debian 13's
`ca-certificates` bundle. The image still runs as `nonroot`, and both amd64 and arm64 images pass
the Image readiness check before any tag is pushed.

## Also in this release

- On Windows, `gcpemu env` against an Instance bound to all interfaces, as the OCI image is, prints
  `127.0.0.1` addresses instead of `[::]`, which gcloud couldn't dial. The Admin API's endpoint
  listings and `endpoints.json` changed the same way: a Service endpoint is never an unspecified
