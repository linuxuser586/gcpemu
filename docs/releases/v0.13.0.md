## Changed: under `CI=true`, only `gcpemu run` takes the CI defaults

Under `CI=true`, every Instance used to start Ephemeral, log JSON and serve no Web console. Now only
the CLI applies those defaults (#802, ADR 0039), so an emutest Instance in CI logs text and serves
the console, as it does on a laptop. `gcpemu run` keeps them, but below the config file,
`GCPEMU_*` variables and flags: `ephemeral: false` in `gcpemu.yaml` now beats the CI default, as
does any other key the file names, zero values included. An empty key still counts as absent.

A CI job that parsed an emutest Instance's logs as JSON now gets text.

## A VM runtime's own `docker push` reaches the registry

On Docker Desktop, Colima, OrbStack and Podman machine, `docker push` runs inside the runtime's VM,
where `localhost:4561` is the VM's own loopback, so pushes to `$GCPEMU_REGISTRY` failed with
`connection refused` or `i/o timeout` (#831). An Instance on the host now starts a Registry relay
there in the background: a container in the VM's host network that listens on `127.0.0.1` at the
registry's port and forwards to the registry (ADR 0043). `docker push` and `docker pull` with
`localhost:4561/LOCATION-docker.pkg.dev/...` now work from the host and the VM alike, with no
`insecure-registries` entry. The `docker save` and `crane push` workaround in the v0.12.0 notes is
no longer needed.

- **Podman machine** sends `localhost` registries HTTPS. Push with `podman push --tls-verify=false`,
  or add `[[registry]]` with `location = "localhost:4561"` and `insecure = true` to
  `/etc/containers/registries.conf` inside the machine (`podman machine ssh`). `gcpemu doctor`
  prints that step.
- On a VM runtime the Instance now creates its services network, the VM relay and the Registry
  relay as soon as it starts, rather than when a Service first needs containers. Start doesn't wait
  for them.
- If something in the VM already listens on the registry's port, the Instance starts without the
  relay and warns; `gcpemu doctor` reports it with the fix.
- A Containerized Instance needs no Registry relay: publish its registry port at the same host port
  (`-p 127.0.0.1:4561:4561`), and the runtime's own `docker push` and `docker pull` reach
  `$GCPEMU_REGISTRY` too (#835).

## emutest reclaims the Instances of interrupted test runs

A test run killed before its cleanup ran (a CI timeout, `Ctrl-C`, a crashed `go test`) used to
leave its containers, networks and volumes behind until `gcpemu prune`. Now the first emutest
Instance a test process starts first reclaims those of earlier runs whose test has ended: every
Ephemeral Instance's temp dir and every `WithTestDataDir` dir whose owner lock is free (#846,
ADR 0047). Dirs named with `WithDataDir` are never swept.

## GKE restarts a cluster's exited Cluster server

When a RUNNING cluster's Cluster server exits, the GKE Service now logs a warning with the exit code
and the tail of the k3s log, and starts it again on the same volume (#840, ADR 0045). The API
endpoint and the kubeconfig stay the same. If it exits a third time within 10 minutes, the cluster
becomes `DEGRADED`, its `statusMessage` holds the log tail, and `/_emu/v1/ready` fails naming it.
Stopping and starting the Instance brings a `DEGRADED` cluster back.

## Load balancers serve a URL map's `customErrorResponsePolicy`

On global `EXTERNAL_MANAGED` load balancers, a backend status listed in the policy of the matched
route rule, path rule, path matcher or URL map is now answered with the page from the policy's
`errorService`, a backend bucket or backend service, with `overrideResponseCode` as its status
(#844, FR-LB-012). Cloud CDN caches the error page under the requested URL. If the page can't be
fetched, the client gets the original status, nothing is cached, and the request log says
`custom_error_response_fetch_failed` (ADR 0048).

## New image: `gcpemu-echo`

Each release now also publishes `docker.io/linuxuser586/gcpemu-echo` for amd64 and arm64, signed
like the gcpemu image (#862). It's the Conformance suite's test backend: it answers
`/status/<code>` with that status and every other request with a JSON report of it, keeping only
the headers named in `ECHO_HEADERS`, and listens on `PORT` (8080 by default) so Cloud Run can run
it.
