## A VM runtime's own `docker push` reaches the registry

On Docker Desktop, Colima, OrbStack and Podman machine, `docker push` runs inside the runtime's VM,
where `localhost:4561` is the VM's own loopback, so pushes to `$GCPEMU_REGISTRY` failed with
`connection refused` or `i/o timeout` (#831). An Instance on the host now starts a Registry relay
there in the background: a container in the VM's host network that listens on `127.0.0.1` at the
registry's port and forwards to the registry (ADR 0043). `docker push` and `docker pull` with
`localhost:4561/LOCATION-docker.pkg.dev/...` now work from the host and the VM alike, with no
`insecure-registries` entry. The `docker save` and `crane push` workaround in the v0.12.0 notes is
no longer needed.

- **Podman machine** sends `localhost` registries HTTPS. Push with `podman push --tls-verify=false`,
  or add `[[registry]]` with `location = "localhost:4561"` and `insecure = true` to
  `/etc/containers/registries.conf` inside the machine (`podman machine ssh`). `gcpemu doctor`
  prints that step.
- On a VM runtime the Instance now creates its services network, the VM relay and the Registry
  relay as soon as it starts, rather than when a Service first needs containers. Start doesn't wait
  for them.
- If something in the VM already listens on the registry's port, the Instance starts without the
  relay and warns; `gcpemu doctor` reports it with the fix.
- A Containerized Instance needs no Registry relay: publish its registry port at the same host port
  (`-p 127.0.0.1:4561:4561`), and the runtime's own `docker push` and `docker pull` reach
  `$GCPEMU_REGISTRY` too (#835).
