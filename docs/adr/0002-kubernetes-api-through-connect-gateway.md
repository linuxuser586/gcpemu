# The Web console reaches Kubernetes through an emulated Connect gateway

The GKE view shows namespaces, workloads, pods and pod logs, which only a cluster's Kubernetes API server knows. A browser cannot call the API server itself: it presents a per-cluster CA, wants client certificates and sends no CORS headers. The console may only call public GCP APIs and `/_emu/v1` (FR-UI-003), so instead of adding a console-private proxy we emulate a subset of GKE's Connect gateway (`connectgateway.googleapis.com/v1/projects/P/locations/L/gkeMemberships/M/...`), the public API through which Google's own console and `kubectl` reach fleet clusters.

Every GKE cluster is an implicit fleet membership with the cluster's name, so there is no GKE Hub API to emulate. The location may be the cluster's location, its region or `global`, and the Project may be given by ID or number. The gateway checks `gkehub.gateway.<verb>` on the membership, then forwards the request with the cluster's admin client certificate and `Impersonate-User` set to the caller's Principal, dropping the caller's own credentials and impersonation headers. The API server's IAM webhook and RBAC therefore decide what the caller may do, as they do for `kubectl`.

We rejected an admin API proxy (`/_emu/v1/gke/...`). It would be simpler, but it would run as cluster admin, so the console would see more than its Principal is allowed to, and the Principal switcher (FR-UI-004) could not show what IAM allows. The cost of our choice is a third mount on the GKE Service and fleet semantics we simplify: there is no registration step, and memberships cannot be listed.
