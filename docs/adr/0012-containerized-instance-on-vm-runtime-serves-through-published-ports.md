# On a VM runtime, a Containerized Instance serves host clients through its own published ports

A Containerized Instance starts no VM relay (ADR 0005), because it is already on every network. On Linux the host routes to those networks, so a GKE `LoadBalancer` Service reports node addresses there (#276). On a VM runtime the host cannot route into the VM, so those addresses time out (#280). Managed containers that exist before their host clients, such as Cloud SQL instances and the GKE API server, publish their own ports when they are created. A `LoadBalancer` Service appears after its nodes are running, and a runtime cannot add ports to a running container. We decided that on a VM runtime, a Containerized Instance serves each `LoadBalancer` Service on a port its own container publishes, and reports the host side of that binding. It prefers a published port equal to the Service's port, and otherwise takes a free one from `--port-range`. It learns the host side by inspecting its own container. On Linux nothing changes.

A Containerized Instance can't probe the host's routing from inside its container. It guesses that it is on a VM runtime from the runtime's info (Docker Desktop, OrbStack), and `GCPEMU_VM_RUNTIME=true|false` overrides the guess, for Colima, Podman machine and Linux CI. The setting names the condition, not the VM relay, which a Containerized Instance never starts. When no published port is free, the Service's ingress stays empty, as on GCP while a load balancer is being provisioned. The Instance does not report an address that times out.

## Considered options

- **Publishing ports on the node containers**, as Cloud SQL and the API server do. Services appear after nodes start, so this would mean publishing a NodePort range on every node up front, or recreating nodes whenever Services change.
- **A per-cluster relay container on the external network** with published ports, recreated whenever the set of Services changes. That is a second relay mechanism beside ADR 0005's, and recreating it drops connections.
- **Not supporting it** and pointing macOS users to the native binary with the VM relay. That is cheap, but the image is the documented way to run the emulator under compose.
- **Using published ports whenever the container has any**, with no VM-runtime guess. A Linux user who publishes a range for other reasons would silently lose the node addresses.

## Consequences

- Users on a VM runtime must start the image with `--port-range` and publish that range (`-p 127.0.0.1:20000-20019:20000-20019`). The emulator listens on `0.0.0.0` in its container, so Pods on VPC networks can reach those ports too.
- The ingress is the binding's host IP, usually `127.0.0.1`. The port is usually not the Service's port, so the real `host:port` appears only in the `gke:` endpoint and `gcpemu env`, as on the VM relay path when a Service's port is taken. Only TCP Service ports are served.
- Servicelb is turned off when a cluster's server is created, which the Instance does again each time it starts. A cluster last started under another guess or override keeps unreachable node addresses until the Instance is restarted with the setting it should have. `gcpemu doctor` reports the decision and flags such clusters.
- Other listeners with a dynamic port would also take ports from `--port-range`, leaving fewer for Services. On a VM runtime the Google front end's dynamic port therefore stays outside the range. To learn the decision that early, the Instance connects to the container runtime when it starts, but only in a container with a `--port-range` set.
- Cloud SQL follows this rule with its own containers (#290). Every connector dials port 3307, so on a VM runtime each instance with a public IP publishes 3307 (and 5432 when free) on a `127.0.0.x` of its own, chosen as on the VM relay path (ADR 0005), and reports it as its `PRIMARY` address. A Containerized Instance can't see the host's loopback aliases, and the runtimes differ when one is missing: Docker Desktop and Podman machine refuse the binding, while OrbStack and Colima start the container and never forward it. So `GCPEMU_LOOPBACK_ALIASES=auto|true|false` says whether to use them. `auto` tries them only on Docker Desktop, falling back to `127.0.0.1` when the binding is refused, and elsewhere uses only `127.0.0.1`. `true` tries them anywhere. With only `127.0.0.1`, a second public instance is refused with `FAILED_PRECONDITION`, as on the host. On both paths 3307 is required on the address and 5432 is best-effort, so a local PostgreSQL on `127.0.0.1:5432` does not block connectors.
- Forwarding rules follow this rule on every runtime, not only on a VM runtime (#289). A forwarding rule listens on a loopback alias inside the Instance's container, and `-p` forwards to the container's network interface, never to its loopback, so even a Linux host can't reach it. Listening on the container's own IP instead would work on Linux, but the container has one IP per network, and external Application Load Balancers allow only ports 80, 8080 and 443, so two rules would soon collide on a port. Unlike GKE node addresses, nothing reachable is lost by also using published ports on Linux. So in every Containerized Instance each forwarding rule is also served on a published port, preferring one equal to its own port and otherwise a free one from `--port-range`, with whoever binds first winning against GKE Services. `GCPEMU_LB_<NAME>` reports the host side of that binding, and stays unset (with a warning saying what to publish) while none is free. The in-container loopback listener stays as well, for clients inside the container and the emulated DNS. Without the Docker socket the Instance can't inspect its own published ports, so it listens on `0.0.0.0:<rule port>` in its container (the first rule on each port wins) and reports `127.0.0.1:<rule port>`, which is right when the port is published at the same host port. Because forwarding rules now draw from `--port-range` on Linux too, the Google front end's dynamic port stays outside the range in any Containerized Instance with a `--port-range`. `gcpemu doctor` lists forwarding rules that have no published port.
