# Instances delegate whole Projects to paired Instances, which trust asserted Principals

A team shares one long-lived Instance on an office machine, as in ADR 0011 and ADR 0021, while each member keeps their own Instance on a laptop. They want a client pointed at the laptop to see the office's Projects too, without a second set of Endpoint overrides. Clients also want APIs that no Service implements, such as Firestore, Spanner or Bigtable, for which Google ships its own emulators. We decided that an Instance forwards requests it does not answer itself to a Delegate: a Linked Instance for the Projects delegated to it, or an External emulator for the APIs delegated to it.

**By Project, never by Service.** A Linked Instance shares a Project, and the front Instance delegates it, and only then does the front Instance forward every request naming that Project, whatever the Service. A Project the front Instance already has cannot be delegated, and a reference to a Delegated Project never creates it locally (an exception to ADR 0001), so local state is never shadowed or merged. Requests that name no Project are routed by what owns them: a bucket by the ownership list the Linked Instance keeps the front Instance up to date with, a service account by the Project in its email, and `projects/-` and aggregated lists by asking every Instance and merging the answers.

**Asserted Principals over Pairing.** The front Instance authenticates each caller and forwards the request over mutual TLS with their Principal asserted. The Linked Instance accepts the assertion only from an Instance it has paired with, and checks IAM itself at its own IAM enforcement level. A service account of a Delegated Project gets its access tokens from the Linked Instance, so when a caller presents a token the front Instance did not issue, the front Instance asks the Linked Instances it delegates to whose it is, keeps the answer briefly, and asserts it only for a service account, or a Federated principal, of a Project delegated to the Instance that answered. Unlike passing tokens through, this keeps the trust within one Pairing, never sends Foreign credentials over a link, and costs a round trip per new token rather than per request. Pairing is approved on both sides, and each side pins the other's Instance CA. Discovery over mDNS/DNS-SD only lists Discovered Instances and never pairs them, and only Instances bound with `--link-bind` advertise.

**Data plane addresses by caller.** A Linked Instance answers a request that came over a link with the addresses its LAN listeners (`--gke-bind`, `--ar-bind`, `--lb-bind`, `--gfe-bind`, `--sql-bind`) serve, as the metadata server picks its universe by caller (ADR 0009). Clients then reach the Data plane directly, through the same credential checks as any LAN client. A Data plane that is not bound on the LAN is reported as unavailable over the link, never as a loopback address that would be wrong on the caller's machine. The URLs in credentials an Instance issues, such as a key file's token endpoint, name the address the caller used, whoever the caller is, unless it came by a real Google hostname: over a link that is the front Instance the request came through, and at a `--bind` address it is that address as the caller dialled it, not the configured gateway, which a wildcard `--bind` reports as loopback.

**Delegated APIs are a passthrough.** An External emulator ignores credentials, and the emulator has no permission map for APIs it has no Service for. The front Instance forwards REST and gRPC as they come, including through the Google front end in Host mode, does not check IAM, and claims no Fidelity for them. On `--gfe-bind` it still requires credentials the Instance issued before forwarding.

## Considered options

- **Delegating a single Service**, such as `gke` to a bigger machine. GKE pulls from Artifact Registry, Workload Identity takes tokens from `iam`, pods reach Cloud SQL private IPs, and Secret sync reads Secret Manager, all within one Instance. Splitting Services across machines breaks each of these, while a whole Project keeps them together.
- **Passing the caller's token through**, and having the Linked Instance ask the issuing Instance to validate it. It costs a round trip per request, and a Linked Instance would have to trust every Instance that can issue a token, not only the ones it paired with.
- **Real credentials only**, as on `--gfe-bind`. Each team member would need a key issued by the office Instance, and the front Instance's own login would mean nothing for a Delegated Project.
- **Linking automatically**, by shared secret or for every Discovered Instance. Pairing gives another machine the authority to assert Principals, which must not happen without someone choosing it.
- **Shared or replicated state** across Instances. It is a distributed system, which a local emulator should not become.
- **Linking VPC networks** across machines. That is close to Cloud VPN or Interconnect, which the SRS leaves out of scope.
- **The front Instance relaying the Data plane** and rewriting addresses into its own Loopback aliases. It duplicates the LAN listeners and their credential checks, and puts a second hop on every byte.

## Consequences

- A Delegated Project whose Linked Instance is unreachable fails with UNAVAILABLE, naming it. The front Instance's readiness does not depend on its Delegates, and `gcpemu doctor` reports each link.
- A request naming Projects that no one Instance holds, such as a local subscription to a Delegated Project's topic, or Projects delegated to two links, is refused with FAILED_PRECONDITION rather than routed by the first Project it names, which would fail later on the other Instance.
- Anything that would still create state for a Delegated Project on the front Instance, such as a request naming it only in its body, or a seed, is refused with FAILED_PRECONDITION naming the link, rather than counted as existing, so that local state never shadows the Linked Instance's. Requests naming it are forwarded, so under Strict projects it otherwise behaves as existing.
- Reset and State snapshots act on local Projects only. Links and Pairings are configuration and survive Reset. A Deterministic Instance's guarantee covers local Projects only.
- Creating a bucket whose name exists in either Instance fails with 409, as GCP does for a name taken globally. Only the front Instance enforces it, by the buckets of the Projects shared with it, which the Linked Instance sends it on connect and as they change, and which delegating a Project fetches before it returns. A Linked Instance never learns the front Instance's buckets, so it can still create a name the front Instance holds; a request through the front Instance then reaches its own bucket, which shadows the Linked Instance's.
- A Merged list fails with UNAVAILABLE when any Linked Instance it asks is unreachable, rather than leaving that Instance's items out, since most lists have no way to say that they are partial.
- The ID token certificate endpoints (`/oauth2/v3/certs`, `/oauth2/v1/certs`) are not a Merged list: they list the front Instance's own Signing key, then each Linked Instance's it could fetch, leaving out any it could not rather than failing. The front Instance refreshes a Linked Instance's Signing key whenever its link reconnects, keeps it while the link is down, and forgets it once nothing is delegated to that link (#693). A Linked Instance's Signing key is not scoped to the Projects it shares: it verifies any ID token that Instance signed, as GCP signs every account's ID tokens with the same keys, and verifying an ID token asserts no Principal on the front Instance.
- An STS token exchange names its Project only in its `audience`, so it is routed by the Project of the workload identity pool provider it names, by number or ID (#711). One naming it by ID is forwarded all the same, and the Linked Instance refuses it, as STS wants the number. Its Federated principal is asserted through the front Instance as a Delegated Project's service accounts are, but the pool's attributes stay with the Linked Instance, so `principalSet` bindings on the front Instance's own resources never match it; a `principal://` binding for it does. A forwarded exchange whose Linked Instance is unreachable fails with 503 and OAuth's `temporarily_unavailable`, as STS answers errors, rather than a Google API error.
- An STS token exchange on the front Instance accepts an ID token a Linked Instance signed only for a provider that trusts the Instance's own issuer with no `jwksJson`, and only through a lookup: it asks the Linked Instances it delegates to over `/link/v1/id-tokens`, and takes the answer only for a service account, not disabled, of a Project delegated to the Instance that answered (#702). Answers are not kept, and the token never works as a bearer credential. The certificate endpoints (#693) list a Linked Instance's Signing key unscoped because verifying an ID token asserts no Principal, but exchanging one creates credentials on the front Instance, so it is scoped as access tokens are. With a Linked Instance unreachable, a token no other one claims fails with 503 `temporarily_unavailable` naming the link; a Linked Instance that predates the route (404) does not claim it.
- An access token the front Instance did not issue is looked up on the Linked Instances it delegates to, and a Link that is unreachable (broken, with no `--link-bind` address, or not answering) is never skipped silently (#733). When no reachable Linked Instance claims the token and any Link was unreachable, the request fails with UNAVAILABLE (503 over HTTP) naming each unreachable Link, in every IAM mode, rather than 401 or the default Principal, and that answer is not kept. A Linked Instance that claims the token is believed whatever the others' state.
- Every check of an access token on the front Instance, not only the gateway's, accepts one issued by a Linked Instance it delegates to, through the same lookup (#736): Cloud SQL's ephemeral certificates and IAM database logins, GKE TokenReview, the Artifact Registry login, and the bearer check on the LAN listeners. The lookup sits behind the Instance's authenticator, so a new path that checks tokens gets it too. A Linked Instance answers the lookup only from tokens it issued itself and never asks its own links, so Instances that delegate to each other don't ask each other in circles. An unreachable Link fails each path in that path's own terms, naming the Link, rather than as bad credentials, the default Principal or anonymous access: UNAVAILABLE on the APIs, `57P03` (cannot connect now) on a PostgreSQL login and its equivalent on the other engines, an error in the TokenReview, and 503 from the registry.
- Linked Instances negotiate a protocol version, and an incompatible one is refused at Pairing and on connect, naming both versions.
- A Linked Instance tells a request that came over a link the address of each LAN listener on the `--link-bind` address it arrived at, else the first, as Cloud SQL tells callers arriving through `--gfe-bind` (#619). Every LAN caller, through `--gfe-bind` or at a `--bind` address beyond loopback too, is told GKE's `--gke-bind` address the same way, and no Cloud SQL address without `--sql-bind`.
- Artifact Registry names pkg.dev hosts, not loopback addresses, so over a link without `--ar-bind` a repository keeps its pkg.dev name, which on the caller's machine reaches the front Instance instead. A Repository has no field to say why.
- Load balancing is the exception to Data plane addresses by caller (#669). A forwarding rule's `IPAddress`, and an Address resource's `address`, are the Declared address for every caller, over a link or not, and never blank: the client set them, and rewriting them per caller would show as drift in OpenTofu, or replace the rule. A caller on the front Instance's machine finds a Delegated Project's `--lb-bind` addresses in the front Instance's `gcpemu env`, which merges each Linked Instance's load balancing endpoints as it tells a LAN caller them, under the usual `GCPEMU_LB_*` names (ADR 0013). A rule or Service with no `--lb-bind` address there gets no variable, never a loopback one, and stderr says why; an unreachable link leaves its variables out and is named on stderr, so `eval $(gcpemu env)` still works. GKE Ingress and Gateway status keep the Declared address of the rules behind them. `--lb-bind` serves LoadBalancer Services as well as forwarding rules, and since a Service's ingress lives in the Kubernetes API, read straight from `--gke-bind` rather than over the link, it lists each `--lb-bind` address the Service claimed after its own address, for every caller, rather than being rewritten per caller. A cluster that runs k3s's servicelb, on Docker on Linux, is the exception: servicelb owns its Services' ingress and would overwrite an added address, so there the Service is served on the `--lb-bind` addresses but its ingress lists only its nodes. When two Load balancing frontends want one `--lb-bind` address:port, the winner is fixed by rank, not by which came first, so it is the same after every restart: a newcomer that ranks higher takes the address over, its clients' open connections staying where they were, and `gcpemu doctor` names the one that lost.
- Discovery advertises over IPv4 multicast only, and shares port 5353 rather than holding it: the advertising socket binds the mDNS group address (the wildcard on Windows) with `SO_REUSEADDR`/`SO_REUSEPORT`, and browsing is a one-shot query from an ephemeral port, so the `dns` Service and the OS's mDNS daemon keep the port (#621). Where multicast doesn't reach, `--link-discover` lists static link addresses instead.
- An External emulator is always configured by address. Running one as a Managed container is a separate decision.
