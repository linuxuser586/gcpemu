# On a VM runtime, one VM relay carries all traffic between the host and Managed containers

The SRS left GKE out on macOS, and every container-backed Service assumed the host can route to, and bind addresses on, the runtime's bridge networks. That holds on Linux, but on a VM runtime (Docker Desktop, Colima, OrbStack, Podman machine) those networks live inside a virtual machine. We decided to support every Service on macOS, GKE included, and that an Instance on a VM runtime starts one VM relay: a Managed container joined to every network the Instance uses, which publishes a single control port to the host. The netplane forwarders that Managed containers dial run inside the relay instead of on the bridge gateway, and the emulator's own dials to container IPs (the Kubernetes API, the Edge relay, Cloud SQL's agent, health checks) go through it. Service code keeps addressing containers by their bridge IPs; only the dialer and the listener change.

The relay is used when a probe at start finds the bridge networks unreachable from the host, so Docker Desktop for Linux is treated as a VM runtime too. `GCPEMU_VM_RELAY=1` forces it and `=0` disables it, and Linux CI forces it so that the relay path is tested where a container runtime is available, which hosted macOS runners are not. When the emulator itself runs in a container on a VM runtime (ADR 0003), it is already on every network and starts no relay; host clients reach it through the ports its container publishes from `PortRange`.

The relay publishes only its control port, because a runtime cannot add published ports to a running container. The emulator opens one connection to that port and multiplexes it into streams in both directions, so containers reach the emulator over streams the relay opens, without the relay needing a route to the host. UDP endpoints such as DNS are carried as framed datagrams on a stream. Ports for host clients, which appear while the Instance runs, are bound by the emulator on `127.0.0.1` on the host and carried through the relay to the container.

## Considered options

- **The relay dialing the host** through `host.docker.internal` or its equivalent, with no multiplexing. Each runtime names the host differently, and some not at all.
- **A second code path at every place that dials or reports a bridge IP**, using `host.docker.internal` inward and published ports outward, as ADR 0003 did for running in a container. That is about fifteen paths across GKE, the load balancer, the Edge relay, Cloud SQL, Cloud NAT and host mode, and every new Service would add more.
- **Requiring the emulator to run in a container on macOS** for the container-backed Services. It is the least code, since that mode already works, but the native binary would cover only the in-process Services, and the SRS promises it everywhere.
- **Keeping GKE Linux-only**, as the SRS had it. The relay is needed for Cloud SQL, the load balancer and Cloud NAT anyway, and once it exists GKE costs little more.

## Consequences

- Host clients cannot reach bridge IPs, so on a VM runtime the addresses an Instance reports for host use become `127.0.0.1` and a port the emulator serves there: the GKE cluster `endpoint` (with `127.0.0.1` in the API server's certificate), LB forwarding rules and `LoadBalancer` Services (their own port, or a free one when it is taken), and Cloud SQL. Every connector dials port 3307, and most send no TLS server name (only the Go connector does, and only for instances with a DNS name), so Cloud SQL instances cannot share an address. Each gets a `127.0.0.x` loopback alias when they are installed on the host, and without them only one instance is reachable, on `127.0.0.1:3307`. Fidelity levels do not change; only the addresses do.
- Translated networks (ADR 0004) need VLAN support in the VM's kernel. The relay checks for it, and without it only Translated networks fail.
- Managed containers need a linux gcpemu binary for the VM's architecture. When the host is not linux on the runtime's architecture, it comes from `GCPEMU_AGENT_BINARY`, a `gcpemu-linux-<arch>` next to the executable, or the data-directory cache. A release build otherwise copies it out of the published image for the same version and caches it.
- Host mode remains Linux-only: its blocker on macOS is the host's DNS resolver, which the relay does not solve.
