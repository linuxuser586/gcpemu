# Which scans fail CI and which only report

Until #1165 nothing scanned gcpemu for vulnerabilities or licences. The release built SPDX SBOMs that nothing read, SRS 2.4.2's licence rule was checked by hand at review, and nothing reported the CVEs of Product images (CONTEXT.md), which Renovate never proposes (ADR 0082). We decided on four checks:

| Check | Tool | Runs | On findings |
|---|---|---|---|
| Go vulnerabilities | govulncheck, on linux, darwin and windows | PRs that change `go.mod`, `go.sum` or `.govulncheck-allow.json`; in release before anything is published; weekly on main | **fail** |
| Licences of what gcpemu ships: Go modules, and the console's and setup-gcpemu's production npm packages | Trivy `--scanners license` | PRs that change a manifest, a lockfile or a licence scan exception; weekly on main (#1211) | **fail** on a licence outside the allowed families, or on a package with none; weekly, **report only** its stale scan exceptions, in the image scan's rolling issue |
| Release images | Trivy image scan, HIGH and CRITICAL, fixable only | beside the Image readiness check in CI, and in release before any push | **fail** |
| Product images, Helper images, and Release images built from main | Trivy image scan, HIGH and CRITICAL (`just image-report`) | weekly | **report only**: a job summary, and one rolling issue |

- **govulncheck for Go, not Trivy.** govulncheck follows the call graph, so it fails only when the code calls a vulnerable symbol, not on every vulnerable module in go.sum. It runs as `go install golang.org/x/vuln/cmd/govulncheck@<exact version>`, so go.mod gains nothing and devtool stays stdlib-only (ADR 0061). It analyses each GOOS the binary ships for, since build constraints hide platform-only calls from the others. The release runs it before publishing the binaries, so they are held to the bar its images are. Trivy still scans the Go binaries inside the Release images, where it reports the same stdlib vulnerabilities by CVE.
- **The licence rule covers what gcpemu ships.** SRS 2.4.2 is about the product's third-party dependencies, so the check reads go.mod and the production dependencies of the console, which the binary embeds, and of setup-gcpemu, whose `dist/` is committed and run by users. go.mod counts in full: Go has one module graph and cannot tell a test-only module from a shipped one. npm devDependencies are left out, as Trivy does by default, and so are the compat suite's Maven POM and client pins, which are never shipped.
- **Licences only, on the Node lockfiles.** Dependabot alerts and Renovate's vulnerability PRs already cover their CVEs; a second report of the same advisories would add noise and no signal.
- **The allowed licences are SRS 2.4.2's list read as families**: Apache-2.0; MIT and its variants (MIT-0, X11); every BSD variant, 0BSD included; ISC, the OpenBSD project's licence, which is the two-clause BSD licence reworded; and MPL-2.0. An SPDX expression passes when an OR has one allowed side and an AND has all. The SRS text is left as it is; this ADR records how it is read.
- **BlueOak-1.0.0 is admitted beside those families** (#1200). It belongs to none of them, but it is OSI-approved, has no copyleft and grants patents, as Apache-2.0 does. It reaches setup-gcpemu's shipped `dist/` through glob, minimatch, lru-cache and their kin under `@actions/artifact`, `@actions/cache` and `sigstore`; avoiding those packages would drop artifact upload, caching and sigstore verification. It was first let through by an expiring scan exception, which this replaces. Any other licence outside the SRS families is admitted the same way, one at a time, by amending this ADR with its reason, never by a blanket rule such as "any OSI-approved permissive licence".
- **A package with no licence fails.** Without a licence, nothing is granted, which is worse than a disallowed licence. Trivy reports no finding for such a package, so its scan exception lives in `.licence-exceptions.json`, keyed by Trivy's exact `name@version`, so a new version is looked at again. A lockfile Trivy reads no licence from at all also fails, because its dependencies were not installed and nothing was checked.
- **A shipped package with no licence, on a code path gcpemu never runs, may be stubbed** (#1202). npm `overrides` replaces it with a local stub package that throws a clear error, and a test checks that the path stays unused. setup-gcpemu stubs `unzip-stream` this way: `@actions/artifact` uses it only to download artifacts, the action only uploads them, and it pulls in `buffers@0.1.1`, which declares no licence. A scan exception would be renewed forever, and reimplementing the package would ship code nobody calls.
- **Trivy is installed as a binary checked against a per-platform sha256**, by `.github/install-trivy.sh`, like OpenTofu. Never `aquasecurity/trivy-action` or `setup-trivy`: their tags were hijacked in March 2026, and a mutable action tag in a release job is a supply-chain path into signed images. Renovate lists new Trivy versions as a report-only checksum pin. devtool reads the script's version as the one the local recipes require.
- **Scan exceptions expire.** Trivy findings are suppressed only in `.trivyignore.yaml`, govulncheck findings only in `.govulncheck-allow.json`, and packages without a licence only in `.licence-exceptions.json`. Each scan exception names a gcpemu issue and an expiry date, from which (00:00 UTC) it stops holding, as Trivy applies `expired_at`. An expired one, or one without both, fails its check. `.trivyignore.yaml` stays in block-style YAML, the subset stdlib-only devtool reads.
- **A stale scan exception fails the check that judges it** (#1205). An entry is stale when the scan that judges it matched no finding to it; one match keeps it. Only a scan that sees everything an entry could cover may call it stale, and a stale entry is reported as stale, not as expired, since the fix is to delete it:

  | Exception file / section | Judged by | On a stale entry |
  |---|---|---|
  | `.govulncheck-allow.json` | `just vulncheck`, whose one run covers linux, darwin and windows | **fail** |
  | `.licence-exceptions.json` | `just licence-check`, and the weekly `just image-report -licences` (#1211) | **fail** on a PR; **report** weekly in the rolling issue |
  | `.trivyignore.yaml` `licenses:` | `just licence-check`, and the weekly `just image-report -licences` (#1211) | **fail** on a PR; **report** weekly in the rolling issue |
  | `.trivyignore.yaml` `vulnerabilities:` | the weekly `just image-report` only | **report** in the rolling issue |
  | any | `just image-scan <ref>`, one image | never judged |

  For `.govulncheck-allow.json`, a match is a called finding only: an uncalled one never fails the check, so an entry left holding only uncalled findings is stale. A finding counts as matched whether or not the entry let it pass, so an expired entry whose finding is still there is reported as expired. The weekly report sees only HIGH and CRITICAL findings, the only ones any image scan fails on, so a `vulnerabilities:` entry for a lower severity reads as stale. `just licence-check` judges nothing when a lockfile went unread. A PR runs it only when it changes dependencies, so the weekly report runs the same scan over main's installed dependencies, so that an entry a merged bump left stale is reported within a week rather than failing some later, unrelated lockfile PR. When a lockfile went unread there, or the scan could not run, it judges no licence entry and says so in the rolling issue, even when nothing else is reported, since nothing else would announce it; a scan that could not run also fails the run. The weekly report judges nothing when any image could not be scanned, or no Release image was given, and says so instead, since the missing image might be the one an entry still holds for. Trivy applies `.trivyignore.yaml` itself, so devtool sees what it suppressed only through `--show-suppressed`, experimental in Trivy 0.76, which adds `Results[].ExperimentalModifiedFindings` with the ignore file as `Source`. If a Trivy bump renames that field, every entry reads as stale and the check goes red: it fails loudly, never silently.
- **A Product image finding never fails CI.** Refreshing a Product image changes what the emulator promises, so it is a deliberate change (#895), not something a CVE published overnight should force into an unrelated PR.
- **The weekly scans keep rolling issues.** Each keeps one issue open while it has something to report, updates it each week, and closes it on the first run with nothing: "Weekly scan: image findings and stale or expiring scan exceptions" for fixable HIGH and CRITICAL vulnerabilities in Product, Helper and Release images, stale `.trivyignore.yaml` `vulnerabilities:` and `licenses:` entries and stale `.licence-exceptions.json` entries (#1211), and "Go vulnerabilities called on main" when the weekly govulncheck fails. The image issue is closed only after a run that scanned every image in every list, so a partial scan is never an all-clear. Only a run on main touches the issues; a run dispatched from a branch reports in its job summary alone. It also lists every scan exception that stops holding within two weeks, since an expired Release image exception fails the scans of every PR that changes code.
- **Helper images are scanned too, report only** (#1203). `devtool helper-images` lists them from `renovate.json`: every docker custom manager is a Helper image (ADR 0082), and its reference is the tag its regex reads from its files, by the same code `internal/devtool/renovate_test.go` checks them with. `just image-report` scans them with the Product images, using the same Trivy flags and `.trivyignore.yaml`, and reports them in a section of their own; a reference in both lists (GKE's k3s is also the Edge relay's) is scanned once and shown in both. A finding never fails CI: its fix is a Renovate bump once upstream ships one, or a report upstream.
- **The weekly report scans the Release images too** (#1205), so its `vulnerabilities:` judgment sees every image an entry could hold for. It builds `gcpemu` and `gcpemu-echo` from main for the runner's own architecture, as CI's e2e job builds `gcpemu:check` and `gcpemu-echo:check`, and reports them in a section of their own, report only like the others. The release workflow's gating scan is unchanged.
- **The list of Product images comes from the code.** `devtool product-images` prints the values the emulator runs (Cloud SQL's postgres images, GKE's k3s, the system images it preloads and the add-on manifests' images, the Managed emulator images), and a test fails when an image in those files is missing from the output. No workflow keeps its own list.
- **Trivy's database is cached** by `actions/cache`, keyed by day and runner OS, so a runner OS normally downloads it at most once a day.

## Considered options

- **Trivy for Go vulnerabilities as well.** One tool fewer, but it reports by module version, so every vulnerable package anywhere in go.sum would fail CI whether or not gcpemu reaches it.
- **SARIF upload to GitHub code scanning.** Findings would show in the Security tab, but the job summary and the rolling issues already reach the maintainer, and code scanning adds a second place to triage.
- **Failing on Product image CVEs.** It would block unrelated PRs on a CVE published in an upstream image, and the fix, a Product image refresh, needs a deliberate change of its own.
- **The SRS list read literally** (Apache-2.0, MIT, BSD-2/3-Clause, MPL-2.0 only). ISC and 0BSD are the same terms as licences it allows, and an expiring exception for each would be renewed forever.
- **Avoiding BlueOak-1.0.0 packages** (#1200). They reach setup-gcpemu only through `@actions/artifact`, `@actions/cache` and `sigstore`, so dropping them drops what those do.
- **Admitting any OSI-approved licence with no copyleft.** It would widen SRS 2.4.2 past how this ADR reads it, without anyone deciding the next licence.
- **Licences of every dependency**, devDependencies and the compat POM included. Build and test tooling would face a rule written for the product, and Trivy fetches the POM's parents from Maven Central, which answers a burst with 429 and blocks the address for a while.
- **Packages without a licence as warnings.** Trivy can't suppress them, but a warning nobody must act on lets an unlicensed package ship.
- **Exceptions without expiry.** Simpler, but a suppressed finding would outlive its reason unnoticed.

## Consequences

- Main starts with scan exceptions: Go 1.27.3's net/http (GO-2026-6859, CVE-2026-97054 in the images; #1198), hamba/avro/v2, which has no fixed version (#1199), and buffers@0.1.1, which declares no licence (#1202).
- `just licence-check` needs the dependencies installed (the Go module cache, `node_modules` in console and setup-gcpemu).
- `just doctor` does not require Trivy; the Trivy recipes name the version to install when it is missing. `.github/install-trivy.sh` covers Linux and macOS, where CI runs Trivy; on Windows, install that version by hand. `devtool product-images` runs a separate package, `internal/devtool/productimages`, because the list lives in the emulator's packages and devtool itself stays stdlib-only (ADR 0061); that recipe builds most of the module.
- A Product image that cannot be scanned (a registry's rate limit, say) fails the weekly run after the others are reported.
- A new advisory against a toolchain or module the code calls stops the next release, and fails a Release image's push when its stdlib is affected, until the fix lands or a scan exception is added.
- A Helper image that cannot be scanned fails the weekly run the same way. A docker custom manager whose files hold no tag, or disagree on it, stops the whole weekly image report before any scan, since its list would be wrong; `TestRenovateHelperImagesListed` fails on the same drift in CI first.
- This replaces ADR 0082's licence reminder on major and replacement PRs: the licence check covers every change to a lockfile, minors and transitive dependencies included.
